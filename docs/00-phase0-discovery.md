# Phase 0 — Walmart discovery log (2026-10-05)

Every fact about walmart.com in this project's code traces to a numbered
experiment below. Scripts: `probe.py`, `probe2.py`, plus one-shot runners
(kept in shell history, artifacts in `debug/`).

## The question

Ralph Lauren (the sibling project) scra​pes per zip via a public SFCC
endpoint (`StoreInventory-Inventory?pid=<pid>&zipCode=<zip>`). Does
walmart.com offer anything equivalent? **Short answer: no public
zip-in-URL API exists; the working mechanism is steering the store-finder
page's own search to a zip via a browser action.**

## Experiment log

| # | Experiment | Result |
|---|---|---|
| R1 | `browserHtml + scrollBottom` on `/search?q=milk` | ✅ 200, 1.9MB real HTML, 57 products in `__NEXT_DATA__`. **No blocks.** Regex lesson: match `script#__NEXT_DATA__` by id only (tag carries `nonce=`). |
| R2 | Same PDP in two sessions, `setLocation` zip 10001 / 90210 | ⚠️ Action reports `success` but **both** resolve to `Sacramento 95829 / store 3081` (Zyte IP's default). Walmart ignores the browser geolocation override — location = **IP geo + server-side state**. |
| R3 | Cookie dump of both sessions | No zip-like cookie. Location is bound server-side to the **`ACID`** anonymous-customer cookie. |
| R4 | Raw HTTP GET `/api/store/v1/stores?zip=10001` | ❌ 521 Akamai error shell. **Raw HTTP is blocked, period** (also kills robots.txt: 503). |
| R5 | `browserHtml` of `/store/finder?zip=10001` | Renders stores — but **for the session's default location** (Sacramento), not the URL zip. `?zip=` only pre-fills the form. |
| R6 | `networkCapture` on a healthy page load | Revealed Walmart's 2026 API layer: **persisted GraphQL via GET** — `/orchestra/<app>/graphql/<Operation>/<sha256hash>?variables={...}`. |
| R7 | Zyte action-name discovery | `type` (with `text`), `evaluate` (with `source`), `waitForTimeout` (no fields, fixed pause), `waitForSelector` (`timeout` in **seconds**, max 15). `insertText`/`pressKey` do not exist. |
| R8 | PDP store-chooser panel via UI actions | Flaky: click lands pre-hydration → no-op; success needs settle-waits. Panels opened ~1 in 4 attempts. |
| R9 | Challenge shells | Some loads return ~500KB, **no `<title>`**, no product data, "challenge" marker — while `__NEXT_DATA__` may still exist. Production needs shell detection + retry (`walmart/middlewares.py`). |
| R10 | Bundle mining (229 PDP + 86 finder chunks from i5.walmartimages.com — CDN, freely fetchable) | 136 GraphQL ops found via `{type:"query",name:"...",hash:"..."}` pattern. Key find: **`storeFinderNearbyNodesQuery`** (finder's zip→store search). |
| R11 | Replay `storeFinderNearbyNodesQuery` via `evaluate`+`fetch` | ❌ **Access Denied** — Walmart's GraphQL requires security headers (`WM_SEC.AUTH_TOKEN` etc.) generated by their own JS. Direct API replay is dead; the page's own code must make the call. |
| R12 | **Steering**: `evaluate` types zip into the finder combobox (React native-setter + input event) | ✅ **Page's own search re-renders store cards for the typed zip**: 50 LA stores for `90210` from a Sacramento-IP session. This is the production mechanism (`walmart/steering.py`). |
| R13 | Clicking "Make this my store" (native action click) to pin the session | Click `success`, but session stays Sacramento (verified via PDP header label *"change Sacramento Supercenter selected"*). The pin does not persist across requests — likely needs an authenticated persist call. **Prices therefore stay at the session-IP default; only the store list is zip-scoped.** |
| R14 | robots.txt via Zyte | ❌ 503 (Akamai blocks raw HTTP). `ROBOTSTXT_OBEY = False` with crawl limited to public SEO pages (`/search`, `/ip/*`, `/store/finder`). |
| R15 | Multi-`evaluate` sequences | Sometimes only the first `evaluate`'s DOM writes survive (page variants/re-renders). Steering therefore uses ONE evaluate + status div (`wm-steer-status`) whose presence in the HTML confirms execution. |
| R16 | 60-second action budget | Actions beyond 60s are `notExecuted`. Budget waits carefully; 4 × `waitForTimeout` after the steering evaluate fits. |
| R17 | Production steering in the spider | ✅ `zip=10001: 48 stores` (NYC metro: NJ/NY/CT), `zip=90210: 50 stores` (all CA). Output files verified zip-correct. |

## What transferred from ralphlauren, what didn't

| Ralph Lauren mechanism | Walmart equivalent |
|---|---|
| `StoreInventory?pid&zipCode` endpoint | none — steering instead (R12) |
| Zyte `setLocation` (unsupported there) | reports success but **ignored** (R2) |
| SFCC session cookies | `ACID` server-side state (R3) |
| per-zip session pools | kept — warmth reduces shells (R9) |
| browserHtml + scrollBottom listing | identical (R1) |
| lazy tile prices → PDP for price | identical (R1 tiles' `priceInfo` empty) |

## Cost note

Every request is `browserHtml` (~seconds each, 60s worst case with
actions). The default crawl is 1 listing + N PDPs (item_limit) + one
steered finder per zip — e.g. zips=2, item_limit=3 → 9 requests.
