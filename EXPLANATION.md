# Walmart scraper — the full story

This document explains *why* the scraper is shaped the way it is. Every
claim here is backed by a numbered experiment in
[docs/00-phase0-discovery.md](docs/00-phase0-discovery.md) (R# references).
The sibling `../ralphlauren` project covers the shared Scrapy/zyte
concepts in depth; this file covers what's different about Walmart.

## The problem with Walmart (vs Ralph Lauren)

Ralph Lauren is Salesforce Commerce (SFCC): your zip is just a query
parameter on a public endpoint. Walmart in 2026 is a custom Next.js
frontend behind Akamai Bot Manager + HUMAN (PerimeterX), and location is
*state*, not a parameter:

- Raw HTTP requests (any `/api/*`) → **521 error shell** (R4). Only
  browser-rendered requests work.
- Walmart resolves your store from the **session IP**, then binds it
  server-side to your anonymous `ACID` cookie (R2, R3).
- The frontend talks to **persisted GraphQL** endpoints
  (`/orchestra/<app>/graphql/<Operation>/<hash>`) that require security
  headers (`WM_SEC.AUTH_TOKEN`, …) generated by Walmart's own JS (R6,
  R11). You cannot call them directly — but the page can.

## Architecture (what the spider does)

```
start()
 ├─ search listing ──────────► parse_listing ──► PDP per product ─► parse_product
 │   (browserHtml+scrollBottom,  (entries from        (browserHtml)     (full fields;
 │    zip[0]'s session pool)      __NEXT_DATA__)                        stash per missing zip)
 └─ per zip: steered finder ──► parse_stores ──► Store[] for zip ──────► flush stash
     (evaluate types zip;          (aria-labels)                        → WalmartZipProduct
      that zip's session pool)                                           → output/<zip>.jsonl
```

### Why one steered finder per zip, not per product

The store list near a zip is product-independent. Ralph Lauren needed a
request per (product × zip) because SFCC's inventory endpoint is
per-product; Walmart's finder is not, so the zip dimension costs **one
request per zip** total. Products scraped before a zip's stores arrive
are stashed in `_stash` and flushed by `parse_stores` — order-independent
joining (`tests/test_spider.py::StashFlushTest`).

### Why `__NEXT_DATA__` parsing instead of CSS selectors

Every Walmart page embeds a complete server-rendered JSON state blob.
JSON-walking (`walmart/page_objects/base.py`) is stabler than CSS: class
names are hashed (`ld_HN`, `css-2b097c-container`), but the JSON paths
(`props.pageProps.initialData.*`) survived every page variant we saw.
One regex lesson: the script tag's attribute order varies (`nonce=`), so
match by `id` only (R1).

## The zip steering mechanism (the core trick)

`walmart/steering.py` generates the `evaluate` action source. Inside the
finder page's browser:

1. find `input[data-automation-id="store-zip-code"]` (the combobox),
2. set its value with the **native input value setter** (React overrides
   `value`, so `input.value = x` is invisible to React — the descriptor
   trick is the standard workaround),
3. dispatch a bubbling `input` event,
4. the page's own React code fires its authenticated store search,
5. store cards re-render for that zip; we parse them from
   `aria-label="Make this my store, <name>, <street>, <city>, ST ZIP"`.

Proven by the sharpest result of Phase 0 (R12): a Sacramento-IP session,
zero location cookies, typed `90210` → 50 LA stores. And the JS writes a
`wm-steer-status` div whose `TYPED` marker must appear in the returned
HTML — if a page variant wiped the evaluate, the spider *refuses to
cache the default-location stores* rather than emit wrong-zip data (R15,
`parse_stores`).

## The zip pinning investigation (what didn't work)

Goal: make *prices* zip-specific by pinning each session's store.

1. **Zyte `setLocation`** — reports `success`, ignored: Walmart reads IP
   geo, not the Geolocation API (R2). (Ralph Lauren rejected the action
   outright; Walmart accepts it and just doesn't care.)
2. **Zip in URL** — `/store/finder?zip=` only pre-fills the form; renders
   default-location stores (R5).
3. **Direct API replay** (`evaluate` + `fetch` of the nearby-stores
   GraphQL with zip variables) — **Access Denied**: needs Walmart's
   security headers (R11).
4. **"Make this my store" click** (native action click, within the 60s
   budget, click reported `success`) — session stayed Sacramento,
   confirmed by the PDP header's *"change Sacramento Supercenter
   selected"* label (R13). The persist flow apparently requires an
   authenticated context the headless session doesn't have.

Conclusion (documented, not guessed): **per-zip prices are out of reach
for anonymous browserHtml sessions.** The honest scope — zip-scoped store
lists + real (session-IP) prices — is what the spider delivers.

## Anti-bot reality & mitigations

| Symptom | Mitigation | Where |
|---|---|---|
| Challenge shells: ~500KB, no `<title>`, 200 status (R9) | rewrite to 503 → Scrapy retry (≤2×) | `middlewares.py` |
| Session warm-ups hitting shells | shell-detector **skips session-init requests** (rewriting them empties the session pool → `Could not get a session ID`) | `middlewares.py` |
| Flaky `evaluate` on page variants | `TYPED` marker required; unconfirmed steer = no cache (never wrong data) | `spiders/products.py` |
| robots.txt 503 via API (R14) | `ROBOTSTXT_OBEY = False`; crawl limited to public pages `/search`, `/ip/*`, `/store/finder` — a documented trade-off, not an accident | `settings.py` |

Shell-detector middleware priority is 560 — **above** RetryMiddleware's
550, because `process_response` runs highest-priority-first: we rewrite
*before* Retry sees the 503.

## Cost model

Everything is `browserHtml` (~30s mean in our runs, 60s cap with
actions). Requests per run = 1 listing (+`page_limit`-1 extra pages) +
`item_limit` PDPs + 1 finder per zip. Default smoke run (3 products,
2 zips) = 9 requests. Raise `item_limit` / `page_limit` deliberately.

## Testing

Offline unittests (`tests/`) run against **real captured fragments**
(`tests/fixtures/`): 3 real search items, the real milk PDP JSON, and 6
real 90210 store-card buttons. The spider tests cover zip validation,
request building, and the stash-and-flush join — no network involved.
